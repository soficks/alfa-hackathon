# 2. Цель, границы и пять исходов

Система принимает одну кредитную заявку по общему applicationId,
собирает синтетические данные внутренних/внешних источников, валидирует
и считает факторы риска, свободный денежный поток, скоринг и доступные
условия. Автомат принимает решение только в пределах политики;
пограничные случаи получает сотрудник.

| **Исход**        | **При каких условиях**                                                     | **Клиентский статус** |
|------------------|----------------------------------------------------------------------------|-----------------------|
| Автоодобрение    | Полные данные, нет стопов, группа A/B, DSCR и лимиты проходят              | APPROVED              |
| Автоотказ        | Подтверждённый жёсткий стоп либо финансовый отказ по матрице               | REJECTED              |
| Запрос сведений  | Нет, устарели или противоречат необходимые сведения                        | NEED_INFO             |
| Контрпредложение | A–C, нет мягких стопов; исходные условия непосильны, альтернатива проходит | COUNTER_OFFER         |
| Серая зона       | Мягкий стоп, группа C, пограничные метрики, лимит/залог/полномочия         | IN_QUEUE → IN_REVIEW  |

# 8. Финансовая математика и проверка допущений

## Очищенная выручка

Rev_m = поступления − внутренние переводы − займы учредителей − кредиты
− возвраты − продажи активов − транзит; Rev = ΣRev_m / N, N=6…12

## Денежный поток

CF_m = Rev_m − поставщики − зарплата и взносы − налоги − аренда − прочие
операционные; CF = ΣCF_m/N. Кредитные платежи НЕ вычитать из CF.

## Долговые платежи

DS_current = Σ фактических регулярных платежей кредитам/лизингу; без
графика условная база max(задолженность, 0,3×лимит), n=24 мес.

## Аннуитет

r = annual_rate/12; A = S×r/\[1−(1+r)^(−n)\]; если r=0, A=S/n.
Дифференцированный график: A1=S/n+S×r.

## Базовый DSCR

DSCR = CF /(DS_current + A_new); если знаменатель равен нулю,
предусмотреть определённую ветку обработки.

## Стресс

CF_stress = (1−v)×Rev×(1−0,20)−Fixed; DSCR_stress =
CF_stress/(DS_current + A_new). v — доля переменных расходов; Fixed —
постоянные.

## Сезонность

CV = σ(Rev_m)/Rev; слабый поток — минимум средних CF за любые
последовательные 3 месяца; DSCR_weak = CF_weak/(DS_current+A_new);
тренд=средняя выручка последних 3/предыдущих 3 мес.

## Долг/CF

DebtCF = (остаток текущих долгов + сумма нового кредита)/(12×CF); если
CF≤0 — не делить, зафиксировать неустойчивую платёжеспособность.

## Согласованность

DeclarationDiff=\|выручка_декл−ΣRev_m за тот же период\|/ΣRev_m;
CashShare, TopBuyerShare, баланс операций; все периоды сопоставимы.

Финансовые пороги из приоритетного файла: DSCR auto ≥1,25, пограничный
1,1–1,25, без вариантов \<1,0 → отказ; стресс auto ≥1,0, серая зона
0,9–1,0; DebtCF ≤3 auto, 3–4 gray, \>4 при любом варианте отказ. CV\>0,3
включает DSCR слабого периода. PTI не заменяет DSCR.

# 10. Логистическая функция, коэффициенты и обоснование

Математически воспроизводимая калибровка балла в риск (дана в разделе
7.9): PDO=20 баллов за удвоение шансов возврата, anchor SCORE0=600 при
ODDS0=50:1. Это нормативно НЕ заданные значения, а демонстрационная
конструкция скоринговой шкалы.

factor = PDO / ln(2) = 28.853901; offset = SCORE0 − factor×ln(ODDS0) =
487.122876.

Odds_good = exp((S − offset)/factor); PD = 1/(1+Odds_good).

ЯВНАЯ ЛОГИСТИЧЕСКАЯ РЕГРЕССИЯ НА ОДНОМ ПРИЗНАКЕ «сумма баллов»:
logit(PD)=ln(PD/(1−PD)) = β₀ + β₁×S, β₀=16.882392, β₁=-0.03465736;
PD=1/(1+exp(−(β₀+β₁×S))).

Эквивалентно, с центром в 600: logit(PD) = −ln(50) − \[ln(2)/20\] ×
(S−600); β₀,center=-3.912023; β₁,center=-0.03465736.

Пояснение коэффициентов: β₁=−ln2/20 обеспечивает уменьшение odds дефолта
вдвое при +20 баллах; сдвиг β₀ выбран так, чтобы при S=600
PD=1/51≈1,96%. Это АЛГЕБРАИЧЕСКИ ЗАДАННЫЕ коэффициенты перевода балла в
PD; они НЕ оценены методом максимального правдоподобия и не являются
доказанной вероятностью дефолта на реальных кредитах.

Подлинная многофакторная логистическая регрессия при наличии размеченной
истории:
logit(PD)=θ₀+θ₁×WoE(age)+θ₂×WoE(history)+θ₃×WoE(trend)+θ₄×WoE(tax)+θ₅×WoE(industry).
Источник НЕ задаёт чисел θ₀…θ₅ или WoE: невозможно честно подставить
обученные коэффициенты без выборки невозвратов. Экспертная таблица выше
— действующий MVP-алгоритм, а многофакторную регрессию считать
последующим этапом.

Обоснование весов таблицы — экспертное направление влияния признаков, а
не статистическая калибровка: старше бизнес → больше истории; просрочки
→ выше риск; рост выручки → устойчивее погашение; налоговая дисциплина →
качество исполнения обязательств; отрасль → примерный секторный риск.
Численные разницы баллов требуют подтверждения частотами дефолта по
интервалам. Запрещено выдавать заданные +60/+160 и др. за оценённые
регрессионные коэффициенты.

| **Группа** | **Диапазон S** | **PD на нижней границе** | **Путь**             |
|------------|----------------|--------------------------|----------------------|
| A          | ≥640           | ≈0,50%                   | авторешение возможно |
| B          | 610–639        | ≈1,39%                   | авторешение возможно |
| C          | 580–609        | ≈3,85%                   | серая зона           |
| D          | 550–579        | ≈10,2%                   | отказ по F01         |
| E          | \<550          | \>10,2% у порога 550     | отказ по F01         |

Пример: 4 года (120) + без просрочек (160) + тренд 1,08 (110) + налоги
вовремя (130) + торговля (92) = 612; odds ≈75,8:1; PD ≈1,30%; группа B.

# 11. Лимиты и поиск контрпредложений

A_max = min(CF/1,25, CF_stress/1,0) − DS_current; если A_max≤0 — кредит
не обслуживается. S_DSCR(n)=A_max×\[1−(1+r)^(−n)\]/r (или A_max×n при
r=0). S_debt=3×12×CF−остаток долга.
AutoLimit(n)=round_down(min(S_DSCR,0,5×annual_revenue,product_max,AUTO_AUTHORITY,S_debt),
product_step).

Для ручной зоны лимит считается без AUTO_AUTHORITY, но с лимитом
полномочий сотрудника. Перебор сроков сетки продукта:
S=min(лимит(n),S_request), S≥product_min и все условия автоодобрения
должны выполняться; ранжирование distance=1×\|ΔS\|/S_request
+0,5×\|Δn\|/n_request +0,3×\[залог\]+0,3×\[поручитель\]. В MVP
авторасчёт меняет только сумму и срок; залог и поручитель — ручные
сценарии. Отдать 1–3 альтернативы. Если нет → F04.

В источнике пример 6 млн/36 мес/20,5%: CF 484,2, DS_current 150, базовый
DSCR 1,29, стресс DSCR 0,66; score 612 (B) → контрпредложение 2,6
млн/36, 3,17 млн/48, 3,63 млн/60. ВАЖНАЯ коллизия источника:
предложенный AUTO_AUTHORITY=3 млн делает исходную заявку ручной по G01
(шаг 5) раньше шага 7; пример контрпредложения следует демонстрировать
при повышенном демо-лимите либо явно через ручную ветку. Нельзя скрыто
пропустить G01 ради красивого примера.

# 12. Динамический чек-лист сотрудника

При IN_QUEUE создаются записи проверки на бэкенде; базовые проверки
нельзя считать выполненными только по наличию файла. Они могут
закрываться автоматически доказательствами из синтетического источника,
однако источник и версия данных сохраняются.

| **Код** | **Обязательное условие положительного решения**            |
|---------|------------------------------------------------------------|
| BASE-01 | ИНН/ОГРН(ИП), форма, запись в реестре совпадают            |
| BASE-02 | Статус компании, ликвидация/банкротство проверены          |

# 13. Дерево действий сотрудника и запреты

0\. Пришла IN_QUEUE → назначить сотрудника; IN_REVIEW, SLA 2 рабочих
дня.

1\. Установить код маршрута: Sxx, Gxx, недостающие Dxx, финансовый риск;
сформировать чек-лист.

2\. Нет обязательного документа/он невалиден? → NEED_INFO, запрос
типа/периода/формата/зачем; после проверки пересчёт.

3\. Есть H01–H09/S01X? → запрет одобрения на уровне сервера; проверка
факта через источник, не ручной override.

4\. Проверить конкретные S/G триггеры и доказательства; снять мягкий
риск только с reason_code + evidence + текстом ≥20 символов.

5\. Пересчитать сумму/срок/ставку, платеж, DSCR и стресс; сумма не выше
разрешённого лимита/полномочий; превышение расчётного лимита \>10%
запрещено.

6\. Если одобрение идёт вопреки рекомендации → подтверждение второго
уполномоченного сотрудника (для демо допустим PENDING_SECOND_APPROVAL).

7\. Завершить только если mandatory checks PASSED или допустимо WAIVED;
выполнить атомарную транзакцию решения+истории.

# 15. Жизненный цикл и уведомления

Статусы: DRAFT, SUBMITTED, AUTO_CHECKS, NEED_INFO, IN_QUEUE, IN_REVIEW,
APPROVED, COUNTER_OFFER, SIGNING, ISSUED, REJECTED, DECLINED_BY_CLIENT,
WITHDRAWN, EXPIRED (предложение). В IN_QUEUE ответ сотрудника за 2
рабочих дня; NEED_INFO 10 рабочих дней и 2 цикла; предложения действуют
30 дней. При изменении данных до решения → AUTO_CHECKS, инкремент
version, diff и пересчёт под прежним ID; после принятого решения
редактирование исходной заявки ограничено.

Клиент и сотрудник должны видеть единый статус и решение в разных
браузерах. Для обновления допускается polling /api/revision при
документированном интервале, а не обязательный WebSocket.

# 17. Приёмка: проверяемые сценарии

1\. ООО и ИП с разными наборами обязательных/условных документов; ИП не
запрашивают устав.

2\. Каждая строка карты 7.9 даёт предсказуемый балл; пример суммы 612,
PD ≈1,30%, группа B.

3\. На граничных баллах 549/550/579/580/609/610/639/640 маршруты не
путаются.

4\. Жёсткий стоп запрещает одобрение даже при высоком балле/DSCR;
H03/H04/H07 скрыты в объяснении.

5\. D01–D14 формируют точный запрос и после подтверждения возвращают в
расчёт без нового applicationId.

6\. C и пограничный DSCR направляются в очередь; альтернативные
сумма/срок проходят повторную проверку.

7\. Сотрудник не может «одобрить» при H-коде, незакрытом required-check,
превышении лимита/непосильном платеже.

8\. Изменение данных после проверки делает связанные checks устаревшими,
сохраняет историю; нет дублей.

9\. Одна SQLite база видна клиенту и сотруднику в независимых браузерах
и после перезапуска сервера.

10\. Проверены SLA/истечение сроков/контрпредложение/подписание; Docker,
README, точные зависимости, OpenAPI, тестовые данные.

# 18. Итоговое резюме для разработки

Ядро системы — не одна «магическая» оценка: (1) правила и статус, (2)
проверка данных и документов, (3) финансовая способность обслуживать
долг, (4) экспертная балльная карта и отображение балла в демо-PD, (5)
солвер допустимых предложений, (6) контролируемый человек в серой зоне.
Порядок матрицы строгий: H → D → финансовое/скоринговое отклонение → S/G
→ контрпредложение → автоодобрение. Все проверки и действия сохраняются
по единому applicationId в SQLite.

Для разработчика скоринга приоритетны: таблица характеристик из §7.9,
S=Σpoints, factor=20/ln2, offset=600−factor×ln50,
odds=exp((S−offset)/factor), PD=1/(1+odds), группы A–E; коэффициенты
логистической функции математически заданы, но НЕ обучены на реальных
данных. Для разработчика бэкенда: строгое управление статусами,
идемпотентный пересчёт, источник данных и аудит,
обязательные/условные/рисковые проверки и серверный запрет нарушения
политики. Для демонстрации: прозрачная причина маршрута, 1–3
альтернативы и разные инструкции сотруднику по сработавшим кодам.

Примечание о достоверности: все нормы, пороги и ограничения применяются
как требования данного учебного MVP и требуют утверждения, юридической
проверки и калибровки до реального банковского использования. Ни одна
численная оценка PD не подтверждена историческими данными дефолтов.
